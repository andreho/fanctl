## [Unreleased]

### Added
- **`fanctld`** — the fan-control daemon. It owns the `hwmon` interface: it
  reads the temperatures, applies each fan's mode (curve, kernel auto, off,
  full, or a fixed manual duty) every tick, and serves clients over a Unix
  socket (default `$XDG_RUNTIME_DIR/fanctld.sock`, or `/run/fanctld.sock` for a
  root system service; overridable with `--sock` or `FANCTLD_SOCK`). It is
  designed to run as a systemd service (a ready-made unit ships in
  `systemd/fanctld.service`) and reloads its config on `SIGHUP`. The socket is
  opened up (`0666`) so a root daemon can be driven by a user-space TUI.
- **`fanctlui`** — the TUI client. It renders the state served by the
  daemon and sends fan commands; it no longer talks to the hardware itself,
  so the fans stay under the daemon's control whenever the TUI is closed.
- The one-shot `--probe` / `--summary` modes (and the `-c` config flag) now
  live on `fanctld`.
- **`--summary` now leads with a `PWM channels` section** listing every
  `pwmN` channel of every discovered `hwmon` chip — including channels that
  are *not* in the config — with the raw duty value, duty percent and
  current mode, so you can see which channel to address before configuring
  one.
- **`--set FAN=MODE` on both binaries** — a one-shot, script-friendly way to
  set a fan's mode and exit. `MODE` is a percent (`0`–`100`) or one of
  `auto|off|full`; the flag can be repeated (`--set pwm1=99 --set pwm2=off`).
  `fanctlui --set` sends the mode to a running `fanctld` over its socket (the
  manual duty then sticks, exactly like the TUI dialog); `fanctld --set`
  writes the chips directly and exits without starting the daemon.
- The coarse `0`–`9` TUI keys (fixed 0–90 % levels) are replaced by an
  **`Enter` dialog for setting an exact manual duty (0–100 %)** on the
  selected fan: type the number, `Enter` applies it, `Esc` cancels, and
  out-of-range input is rejected with an inline error.
- `fanctlui` now runs **all daemon I/O in a background job** that it joins
  non-blocking, so a slow or unresponsive daemon can no longer freeze the UI;
  it keeps showing the last good state and retries on the next tick. `Ctrl+C`
  quits (in raw mode it is a key event, not a signal), and running `fanctlui`
  without a real terminal fails with a clear message instead of a blank,
  frozen screen.
- **Curve editor in the TUI** — `e` on a fan opens a modal table for its
  `{temp, duty}` curve and its initial mode: type values into the `temp` /
  `duty` fields (duty `0`–`100`, temp `0`–`150`), `a`/`x` add and delete
  points, `u`/`d` reorder them, `←`/`→` on the `default:` row cycle
  `auto`/`off`/`full`, and `s` saves. Saving sends a new `save-fan-config`
  request: the daemon validates the curve (points strictly increasing in
  temperature), writes the config file **atomically** (temp file + rename, so
  a crash can't corrupt it), and applies the new curve on its next tick — no
  restart or `SIGHUP` needed. A rejected save shows the reason in the dialog;
  `Esc` cancels without saving.
- **Fan calibration (sweep)** — a new routine derives, per channel, the range
  of duty in which a fan actually responds: `c` on a fan in the TUI (or the
  one-shot `fanctld --sweep pwm1 [--step 5] [--settle 3]`) steps the duty from
  0 % to 100 % (10 % per step, 3 s settling — both adjustable), reads the
  tachometer after every step, and stops as soon as the RPM stops rising.
  The TUI stays responsive while it runs (the daemon sweeps in a background
  thread, the fan row shows `calibrating…`, the result lands in the status
  line). A useful measured range (the fan starts somewhere in the middle, and
  its tach actually moves) is saved on the fan in `fanctl.yaml` as
  `duty_min` / `duty_max` (atomic write) and the fan's curve is clamped to
  that range — a 0–100 % curve then maps onto the part of the duty span the
  fan responds to. The fan's previous mode is restored afterwards; a channel
  whose tach never leaves 0 rpm is reported as having no measurable fan (a
  3-wire fan has no feedback wire, so its own electronics decide how far a
  given PWM drives it — most don't spin below ~20–30 % and many saturate
  before 100 %).

### Changed
- **The config parser now also accepts the pre-1.1.0 `[temp, duty]`
  sequence form for curve points**, so configs generated by 1.0.0
  (including the one a root-run of the old binary may have created under
  `/root/.config/fanctl/`) still load; it always *writes* the new
  `{ temp, duty }` mapping form, so a config migrates itself on first save.
- The previous all-in-one `fanctl` binary (TUI that drove the fans
  directly) is gone; the two parts above replace it.
- The per-fan `curve` in `fanctl.yaml` is now a list of `{ temp, duty }`
  mappings instead of `[temp, duty]` sequences, e.g.

  ```yaml
  curve:
    - temp: 30.0
      duty: 45.0
  ```

### Fixed
- The `off` mode (TUI `o` key, `--set FAN=off`, the config's `default: off`)
  no longer writes `pwmN_enable = 0`; it stops the fan with a **0% manual
  duty** instead. On the it87 family (FEAT_FANCTL_ONOFF chips such as the
  IT8792) the kernel driver's off path leaves the fan running at a fixed
  100% in on/off mode, so the previous `off` was indistinguishable from
  "full"; a 0% manual duty is a real stop on those chips (and on the other
  supported drivers as well).
- The `Full` fan mode no longer writes an invalid `pwmN_enable` value. The
  previous mapping used a `4` ("max") mode bit that the it87 driver does not
  have (it only accepts 0–2), so setting a fan to full speed failed with
  `os error 22`; `Full` is now "manual mode at 100%" and chip-auto is
  `pwmN_enable = 2`, both of which the it87 driver accepts.

## [1.0.0] - 2026-09-22

### Changed
- Renamed `thinkfan-tui` → `fanctl`.
- **Generalized to any `hwmon` device**, not just ThinkPads. Temperature
  reading and fan control now go through the `/sys/class/hwmon` sysfs
  interface; the `sensors` subprocess is no longer required (it remains an
  optional display source).
- Added a **per-fan YAML configuration** (`~/.config/fanctl/fanctl.yaml`),
  auto-generated on first run by probing the hardware. Each fan defines the
  temperature it follows, its control strategy, and a temperature→duty
  curve.
- Fan control is now per-fan and selectable: `curve` (fanctl writes the duty
  from the curve each tick) or `kernel-auto` (the chip's own auto-algorithm).
- **A fan's curve can now be driven by several sensors at once** (e.g. the CPU
  *and* one or more GPUs) combined with a per-fan `aggregation`
  (`max`/`avg`/`min`), instead of a single sensor.
- **NVIDIA GPU temperatures and fan RPMs** are read in-process via NVML
  (the `nvml-wrapper` crate, the same library `BDHU/gpuinfo` wraps), with a
  `nvidia-smi` CLI fallback — since the NVIDIA driver exposes no `hwmon` node
  for GPU temperature. GPUs are displayed and can be referenced as
  curve-driving sensors via `hwmon: nvidia` / `sensor: gpu<N>`.
- The TUI gained a selectable multi-fan list (arrows/`j`/`k`) with per-fan
  `a`/`f`/`o`/`0-9` control, a color-coded temperature bar view, sorting
  (`s`), and scrolling.
- Removed the ThinkPad-only `/proc/acpi/ibm/fan` backend and the
  `sudo chown` workaround (not applicable to `sysfs` nodes).

### Added
- `--probe` (list `hwmon` chips with their PWM/temp/fan sensors, **plus NVIDIA
  GPUs**) and `--summary` (one-shot text dump) CLI modes, plus `-c FILE` for an
  alternate config path.
- Unambiguous chip resolution by `hwmonN` when several chips share a name.
- Unit tests for the curve engine, the hwmon reader/writer (against a fake
  `sysfs` tree), config round-tripping, TUI rendering, and key handling.
